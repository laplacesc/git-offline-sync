# 核心逻辑重新设计

状态：分阶段实施中。设计基于 v2.0.9（`5d10949`）；本轮已经接入正式 React/Tauri 应用。

已实现：单窗口双页签及 GitHub 风格深浅主题；外网导入与开发仓库获取引用合并执行；实际引用同步状态查询；共享导出恢复只提交所属游标；Bundle 回传的内容身份、原子接收记录、独立审查工作树和重复接收；固定 OID/远程地址/显式 lease 的推送计划与远程结果核验；已核实推送的当前提交持久标记。详见 [实现与验证记录](./implementation-verification.md)。

下文仍包含后续目标：`format: 2`、refs-only、新流迁移、统一 requestId/operationId、inspectWorkspace，以及 Patch 的统一接收模型尚未实现。当前继续读写 format 1，Patch 保留原有兼容入口；不能把本轮完成理解为整个迁移计划已经完成。

## 1. 目标与边界

应用负责在内网 GitLab 与外网开发环境之间，借助移动介质交换 Git 数据。核心目标是：**每次交换都能说明传递了什么、依赖什么、已经生效到哪里，以及中断后如何继续。**

本次设计采用以下范围：

- 一个项目有一个权威内网出站源；可以关联多个外网开发仓库及 worktree。
- GitLab 是上游代码事实来源；外网镜像保存已接收的上游快照；开发仓库保存开发者的工作。
- U 盘只运送文件，不承担状态协调。应用不能把“导出成功”解释为对端已经收到。
- 回传进入内网审查流程。导入、整理提交和推送是三个独立动作。
- 保留 bundle 为默认载体、patch 为可选载体，保留 Windows/macOS、现有 Git CLI 和 Tauri/React 技术栈。
- 首期继续串行执行变更操作，不增加后台同步服务、数据库、通用工作流引擎或自动合并策略。

多内网写入源、设备间自动发现、数字签名、自动清理历史包不属于本次实现范围。将来增加多个出站源时，需要先定义权威源切换规则。

## 2. 当前实现与设计动因

现有实现已经具备值得保留的保障：镜像与开发仓库隔离、引用事务、原子 JSON 写入、进程间文件锁、导出恢复记录、按 worktree 保存的 rebase 恢复记录，以及取消和超时控制。重新设计应在这些机制上补全业务模型。

| 当前情况                                                        | 影响                                         | 设计方向                                |
| ----------------------------------------------------------- | ------------------------------------------ | ----------------------------------- |
| `InternalView.tsx`、`ExternalView.tsx` 组合多次查询，并自行判断下一步、包能否导入 | 业务规则散落在页面与核心层，界面状态难以解释                     | 核心层返回工作区快照、操作能力和阻塞原因                |
| 两个页面把同步状态读取失败转换为 `null`                                     | 损坏状态与尚未初始化在界面上可能表现相同                       | 明确区分未初始化、可用、读取失败、待恢复                |
| 外网 `staleState` 仅存在 React 内存中                               | 重启或页面重建后，不能继续依赖该标记判断开发仓库是否更新               | 读取实际远程跟踪引用，并记录成功同步的上游快照             |
| `Manifest` 以 `repoId`、`seq`、引用列表描述包，没有独立内容标识和显式快照依赖         | 序号同时承担展示与流程约束，难以描述同号异包及重试身份                | 分离项目身份、同步流身份、包身份、序号和快照身份            |
| 推送确认依赖前端的提交列表及上下文；API 只传分支名和强推开关                            | 前端上下文保护无法约束外部 Git 进程在确认后修改分支               | 后端创建绑定具体 OID 的推送计划，执行前复核            |
| 回传导出的恢复记录保存整份 `MirrorState`，恢复时整体写回；`import_in` 不先检查该记录     | 回传导出失败后先导入新包，再恢复旧导出，会把新的接收游标写回旧值           | 所有共享资源变更先处理恢复记录；按字段归属提交状态，禁止旧快照整体覆盖 |
| 回传没有持久化包接收记录；patch 导入直接扫描 `.patch` 文件，没有读取 manifest         | rebase 后重导旧包可能新增导入分支；patch 缺少统一身份校验和接收恢复边界 | 引入接收记录与独立审查条目，bundle/patch 共用验证入口   |
| `RunnerProvider` 与后端分别分配操作编号，日志按收到事件时的 `activeRun` 分组       | 后台读取日志可能归入前台操作，批处理取消边界不统一                  | 后端操作 ID 贯穿调用、日志、取消和恢复               |

上述文件可直接定位：[前端 API](../src/api.ts)、[内网流程](../src/InternalView.tsx)、[外网流程](../src/ExternalView.tsx)、[操作运行器](../src/runner.tsx)、[日志](../src/LogPanel.tsx)、[Tauri 命令](../src-tauri/src/commands.rs)。恢复覆盖路径见 [sync.rs](../src-tauri/src/core/sync.rs) 的 `ExportJournal`、`finish_export`、`export_back` 与 `import_in`；patch 路径见同文件 `import_patches`。这里的缺口来自静态代码路径核对，尚未新增复现测试。

## 3. 业务模型

### 3.1 五个概念

| 概念              | 职责                       | 不承担的职责                      |
| --------------- | ------------------------ | --------------------------- |
| Project         | 稳定项目身份、主线与发布分支策略         | 不依赖显示名称、目录或某一个根提交作为唯一身份     |
| SourceSnapshot  | 某次已发布/已接收的上游分支与 tag 完整快照 | 不包含开发分支、回传临时引用或 GitLab 内部引用 |
| TransferPackage | 不可变文件集，描述对象载荷、快照或待审查变更   | 不表示对端已导入或 GitLab 已接受        |
| ReviewItem      | 某个回传包内一条分支的审查记录          | 不覆盖用户已有的同名分支                |
| Operation       | 一次有明确输入、效果和恢复入口的执行       | 不把 Git 命令退出码直接等同于业务完成       |

配置档继续管理当前电脑的路径与显示偏好。Project 身份保存在仓库元数据中，不能因复制配置档或修改项目名称而生成新身份。

### 3.2 仓库角色

| 仓库     | 允许的核心写入                      | 与其他仓库的关系                 |
| ------ | ---------------------------- | ------------------------ |
| 内网源镜像  | 从 GitLab fetch、准备出站快照        | 永不由应用执行 push             |
| 外网副本镜像 | 导入上游快照、保存接收游标与回传分配信息         | 作为本地开发仓库的 origin         |
| 外网开发仓库 | fetch、建分支、开发、rebase、生成回传包    | 同步只更新远程跟踪引用，不自动改本地分支或工作区 |
| 内网工作仓库 | 接收回传到专用引用、创建审查分支、rebase、push | 是唯一允许应用向 GitLab 推送的角色    |

角色需要仓库结构与元数据共同验证。路径比较先规范化并解析 Git common directory，防止主仓库与 linked worktree 被当成两个独立写入资源。应用锁不能阻止外部 Git 命令，因此关键写入仍需旧值校验。

### 3.3 不变量

1. 出站包只描述 `refs/heads/*`、`refs/tags/*` 的权威快照，所有引用变更来自同一次固定快照。
2. 外网导入不写开发仓库；开发仓库 fetch 不隐式 rebase、reset 或切换分支。
3. 相同包再次导入返回已有结果；同一流、同一序号对应不同包内容时拒绝处理。
4. 包的对象依赖必须在写引用前验证；序号连续不能替代对象依赖验证。
5. Git 引用提交后即视为已产生效果，不能因后续 JSON 写失败而声称“没有导入”。
6. 回传包、审查分支和推送结果各自有身份与状态；分支名字不承担幂等键职责。
7. 任何读取错误都不重置同步游标；取消不代表回滚。
8. 用户检查过的提交集合必须与最终推送的源 OID 一致。

## 4. 包协议

### 4.1 身份和字段

采用新的 manifest 格式版本，以下称 `format: 2`。这是包协议版本，与应用版本独立。

| 字段                                   | 含义与约束                                          |
| ------------------------------------ | ---------------------------------------------- |
| `projectId`                          | 首次建立内网源时生成的 UUID；外网首次导入后绑定。旧根提交身份保留为迁移核验信息     |
| `streamId`                           | 一条发布流的 UUID；出站和回传各有自己的流。状态遗失后不得在旧流内从 1 重新编号    |
| `direction`                          | `outbound` 或 `return`                          |
| `seq`                                | 流内单调递增的展示及冲突检查编号；不是对象依赖证明                      |
| `packageId`                          | 对规范化 manifest 内容计算 SHA-256，计算时排除该字段自身；内容包括载荷摘要 |
| `payload`                            | 类型、相对路径、字节数、SHA-256；patch 记录排序后的逐文件清单；纯引用包无载荷  |
| `objectFormat`                       | Git 对象格式，导入目标必须兼容                              |
| `defaultBranch`                      | 出站快照的默认分支，必须存在于目标 heads 中；用于设置裸镜像 HEAD         |
| `sourceSnapshotId`                   | 出站包的目标快照；回传包开发时所依据的上游快照                        |
| `requiredSnapshotId`                 | 增量出站包的前置快照；全量包为空                               |
| `refs`                               | 出站包的完整目标引用快照，或回传包选中分支的固定 OID 与基准信息             |
| `createdAt`、`toolVersion`、`repoName` | 展示和诊断信息；不得作为身份判断依据                             |

`SnapshotId` 对项目 ID、对象格式、默认分支和按引用全名排序的 `(refName, oid)` 列表计算 SHA-256。固定 UTF-8 编码与字段顺序；协议只允许整数，不允许浮点数与重复 JSON 键；字符串转义、列表排序和跨语言示例必须在实现协议时形成黄金测试。未知协议版本拒绝导入，不能忽略未知语义后继续。

`packageId` 绑定精确内容；文件搬家或复制不改变身份。重新导出即使代码相同，只要元数据不同也可以是另一个包。重试恢复必须返回原来的包，不能重新生成时间戳或分配新序号。

首次导入需要展示项目名、项目 ID、主线和引用概览，由用户确认绑定到目标镜像。UUID 和摘要用于一致性检查，不构成来源认证。

### 4.2 出站包的三种载荷

| 类型            | 内容                 | 适用情况                      |
| ------------- | ------------------ | ------------------------- |
| `full`        | 目标快照可达的全部对象及完整引用清单 | 首次建立、补齐丢包、重建副本            |
| `incremental` | 相对前置快照新增的对象及完整引用清单 | 常规更新                      |
| `refs-only`   | 完整引用清单，无 bundle    | 只有删除、回退、改名等变化，所需对象已在前置快照中 |

`refs-only` 是明确的协议类型，避免为单纯删除分支传输整个仓库。实现早期可继续使用现有全量回退，协议稳定后再启用优化。

源镜像需用应用私有引用保护增量基线所需对象，直到后继包发布完成；不能假设被上游 force-push 或删除的对象永远不会被 GC。引入私有引用时，上游 fetch 的 refspec/prune 范围必须明确限制在 heads/tags，不能让现有 mirror 的 `refs/*` 映射删除这些引用。导出必须固定源 OID 后生成 bundle，并核对 bundle 头与 manifest 一致，不能分别读取活动分支后拼接结果。

### 4.3 导入判定

按以下顺序执行，结果由核心返回给界面：

1. 校验协议、项目、方向、对象格式、路径边界、文件长度及摘要。拒绝越界路径、重复 ref、重复 patch 文件和逃出包目录的符号链接。
2. 查询本地已接收记录。相同 `packageId` 返回 `alreadyApplied`；同流同号异包返回 `sequenceConflict`。
3. 增量与纯引用包要求 `requiredSnapshotId` 等于当前快照；否则返回缺失依赖。取消默认流程中的通用“允许跳号”开关。
4. 全量包无对象前置依赖，可前进到较新快照；展示被跳过的范围和引用变动。较旧全量包返回 `stalePackage`，不隐式回滚。跨流绑定走明确的重建流程。
5. 执行 bundle 校验和目标 OID 类型、可达性检查；纯引用包同样验证目标对象齐全。
6. 在镜像锁内按预期旧快照和旧引用执行导入。

例如：当前为快照 S10，手中只有依赖 S11 的增量包，返回“需要 S11，补齐包或请求全量”。如果拿到同流较新的全量包 S12，则可以直接恢复到 S12。

回传包彼此独立，不要求按序号连续导入，但必须满足其真实对象依赖。内网缺少依赖对象时明确报告，不把已导出某个出站包当成内网工作仓库一定持有对应对象的证明。

## 5. 四条核心流程

### 5.1 发布内网快照

1. 加锁并优先恢复未完成发布。
2. 根据用户选择 fetch 上游；失败时不使用旧状态冒充最新拉取结果。
3. 固定所有公开引用，形成快照。与上次快照相同则返回 `noChanges`，不消耗序号。
4. 选定 full、incremental 或 refs-only；记录对象基线并生成临时载荷。
5. 校验载荷和摘要，生成不可变 manifest 与发布恢复记录。
6. 发布文件、提交发布游标，最后移除未完成标记。恢复时返回相同包与序号。

保留当前隐藏暂存目录、`.pending` 标记和 `export-pending.json` 的机制。发布记录中增加 `packageId` 和内容摘要，防止恢复时误用同名文件。传输目录拔出时保留待恢复状态，提示接回原目录；不另发相同序号的新包。

### 5.2 接收快照与更新开发仓库

接收分为两个明确结果：`mirrorApplied` 与 `devFetched`。

镜像导入先解包对象，再原子更新公开引用和提交标记。引用事务中同时更新 `refs/offline-sync/applied`，并创建 `refs/offline-sync/receipts/<packageId>`；两者指向同一个保存项目、流、序号、包 ID、快照 ID 和默认分支的 Git blob。前者记录当前游标，后者保留历史接收身份，供重复包和同号异包检查，以及 JSON 索引重建。这些私有 ref 不进入对外包，也不作为开发仓库的 fetch 对象。首期不自动删除接收记录。

这个标记与分支/tag 在同一 `update-ref` 事务中提交。`state.json` 是可重建的索引：标记已更新、JSON 未更新时，恢复过程补齐 JSON；标记未更新时，按旧值校验重试。已有未完成导入必须先恢复，不能让下一包覆盖恢复上下文。默认分支 HEAD 的设置作为 journal 中的独立收尾步骤：兼容最低 Git 版本，不假定 symbolic ref 可以与普通引用一起事务提交。HEAD 与索引收尾完成前不允许从该镜像创建开发仓库。启动时还应比较实际公开引用与快照，外部进程修改镜像后显示 `mirrorDrift`，不能仅凭标记认定正常。

新镜像先在同一父目录的暂存仓库内初始化、校验、导入，再发布到最终路径；目标目录在此期间被创建则中止，不覆盖。目录移动行为需在 Windows/macOS 分别验证。

开发仓库更新只做受控 fetch，并校验 origin 指向绑定镜像。成功后记录对应上游快照；刷新时比较实际跟踪引用，区分 `upToDate`、`needsFetch`、`drifted`、`unknown`。该判断不依赖页面内存。tag 更新策略需要明确：首期延续现有行为，对本地同名 tag 冲突报告阻塞，不自动覆盖开发者 tag。

### 5.3 导出与接收回传

外网导出：固定选中分支 OID、显式基准和上游快照，确定 bundle 依赖对象后导出。回传序号继续由外网镜像统一分配。同一镜像下多个开发仓库共享这条回传流；独立外网镜像使用不同 `streamId`。

外网此时只能确认“已导出”。后续收到上游快照也不能仅凭提交 OID 不同就认定回传未接受，因为内网可能做过 rebase。当前范围不增加跨端审查回执；若需要在外网显示“内网已接收/已推送”，必须另行传递绑定 `packageId` 的回执。

内网接收：

1. 完成格式、身份、摘要与对象校验。
2. 将原始分支 OID 保存到 `refs/offline-sync/inbox/<packageId>/<itemId>`，其中 `itemId` 由源 ref 名计算，避免分支路径冲突。
3. 将全部 inbox 引用与该包的接收标记放入同一个引用事务。接收标记指向该包 manifest 元数据 blob，作为重建接收记录的依据。
4. 从这些引用构建 ReviewItem，并返回 `received`；不移动已有本地分支。
5. 用户选择条目后创建审查分支，默认可放入独立 worktree。原分支名只作为建议名称。

接收重复 bundle 返回同一组 ReviewItem；即使审查分支已 rebase，也不再次生成 `-import-N` 分支。若某条审查分支创建失败，包仍然是已接收状态，可以单独重试该条目。原始 inbox 引用在审查结束前保留，用于核对和恢复。

patch 不能保存原始 Git OID 到本地引用并假定对象存在。它使用相同接收记录模型，但先将已校验文件复制到内网本地收件目录并原子发布，再登记接收；U 盘不作为恢复所需文件的唯一位置。应用 patch 前记录目标 worktree、原 HEAD、文件清单和当前阶段。相同包的重试恢复已有 `git am`，不会重新应用一遍；应用成功后保存结果 OID。补丁生成的新提交 OID 与原始提交可能不同，界面要按应用结果展示。

### 5.4 整理与推送

ReviewItem 状态为：`received → prepared → integrating → readyToPush → pushed`。发生冲突进入 `conflicted`；取消或崩溃根据 Git 状态进入 `needsRecovery`。用户可以将未推送条目标记为 `dismissed`，不删除原始内容。

每条开发/审查分支记录：

- `baseRef`：主线或发布分支名。
- `baseOid`：最近一次确认基准时的上游提交。
- `rangeStartOid`：用户确认的待整理提交范围起点。
- `sourceSnapshotId`：外网开发对应的上游快照。
- `provenance`：显式记录、用户确认的推断、旧格式未知。

分支前缀只提供默认建议。旧分支的基准推断要在 rebase/patch 导出前让用户核对。`rangeStartOid` 必须存在且能解释预期提交范围，不能简单拿当前 `origin/<旧基准>` 替代历史边界。包含合并提交、基准被重写或范围有歧义时，展示提交范围并要求明确处理方式；默认不静默压平或猜测。

沿用当前按实际 worktree 保存的 rebase journal。准备阶段记录旧基准、目标基准及固定 OID；完成后才更新基准信息，中止保留旧记录。恢复同时检查 journal 和 Git rebase/am 状态。

推送拆为两个后端能力：

1. `preparePush` 返回 `planId`、完整源 OID、目标远程与 ref、目标旧 OID、基准 OID、待推送提交与是否需要非快进更新。UI 展示该计划。
2. `executePush(planId)` 重新核对仓库、远程、源 ref 和源 OID；不匹配返回 `planStale`。推送使用固定源 OID 和明确目标 ref。默认只允许快进；获确认的非快进推送使用 `--force-with-lease=<目标ref>:<已确认旧OID>`，不能依赖可能被后台 fetch 更新的跟踪引用。

计划冻结目的地址，拒绝 `mirror` 配置和与计划不一致的 push URL/refspec。计划只在当前进程内有效，重启后重新准备和确认。GitLab 仍可因权限或分支保护拒绝推送。

推送超时、进程退出或取消后不能立即判为未推送：查询目标远程 ref，等于计划源 OID 才可确认该结果；无法核实时进入 `outcomeUnknown`。远程已变成其他 OID 时展示实际状态，不能自动再次强推。`pushed` 只表示该目标分支的推送已核实，不表示已合入主线。

## 6. 操作与恢复模型

### 6.1 操作状态

| 状态               | 含义                         | 可执行动作       |
| ---------------- | -------------------------- | ----------- |
| `running`        | 正在执行可中断阶段                  | 请求停止        |
| `committing`     | 正在提交引用或发布记录                | 等待短暂提交阶段结束  |
| `succeeded`      | 业务效果已核实                    | 查看结果        |
| `noChanges`      | 无需变更                       | 返回工作区       |
| `conflicted`     | worktree 中存在可继续的 rebase/am | 解决冲突后继续，或中止 |
| `cancelled`      | 已停止且已检查本地效果                | 查看已完成的步骤    |
| `needsRecovery`  | 有持久化未完成事务                  | 按记录恢复       |
| `outcomeUnknown` | 远程效果暂时无法确认                 | 重新核验远程结果    |
| `failed`         | 已知失败及已知副作用                 | 按原因修复后重试    |

`cancelRequested` 是独立标记，不是终态。停止请求在准备和 Git 子进程阶段生效；引用提交等短临界段延迟取消直到可判定结果。恢复核验使用独立、受限时控制的上下文，不能因为原操作已取消而跳过必要核验。

### 6.2 持久化与锁

继续使用 JSON 原子替换和操作系统文件锁，按用途保存数据：

| 数据                  | 位置                                             | 权威依据                        |
| ------------------- | ---------------------------------------------- | --------------------------- |
| 本机配置                | 系统应用配置目录                                       | 配置文件                        |
| 项目/发布流信息、出站游标、未完成发布 | 镜像 `offline-sync/`                             | 发布 journal 与不可变包            |
| 外网已接收快照             | 外网镜像                                           | 引用事务内的 applied 标记及实际引用      |
| 内网接收记录和 ReviewItem  | 内网工作仓库 Git common directory 下的 `offline-sync/` | inbox ref、接收标记、审查记录         |
| rebase/am 恢复信息      | 操作所在 worktree 的 Git 目录                         | Git 操作状态和该 worktree journal |

只对有跨命令副作用的流程写恢复记录；只读查询不持久化。审查记录里无法从 Git 恢复的用户决定仍需原子写入与备份，不能把所有 JSON 都视为可丢弃缓存。

共享状态按归属拆成接收游标与回传发布游标，恢复记录只携带本操作拥有字段的预期旧值和目标值，不能序列化整份 `MirrorState` 后无条件写回。提交时在锁内重新读取并检查版本：旧值符合则应用，目标值已存在则视为已提交，其他值进入恢复冲突。这样即使未来放宽操作并发，也不能让回传恢复倒退接收游标。

先锁 Git common directory，再按规范化路径排序锁定其他仓库和传输目录；所有调用沿用同一顺序。首期保留应用内一个变更槽，不为并发引入调度器；跨应用实例靠文件锁约束，同步资源存在未完成 journal 时先恢复。

### 6.3 API 与错误

保留显式业务命令，新增统一操作外壳：

- 前端为每次提交生成 `requestId`；后端去重并返回 `operationId`。事件携带 `requestId`、`operationId`、事件序号与步骤，解决调用返回前已产生日志的关联问题。
- `getOperation(operationId)` 可查询结果，`cancelOperation(operationId)` 定向取消；页面不通过“当前活动操作是谁”猜取消对象。
- `inspectWorkspace` 返回结构化状态、可执行动作、阻塞原因和数据版本。前端只保留表单、选择、展开状态。
- 批量同步开发仓库作为一个后端操作，逐仓库记录结果，并在启动下一项前检查取消；已成功项不回滚。
- 错误返回 `code`、`message`、`details`、`recoveryAction`、`operationId`，不要求前端解析中文字符串。展示字段和日志沿用脱敏规则。

工作区查询不是跨 Git、JSON、U 盘的全局事务。返回 `observedAt`、各资源版本及 `consistent/refreshRequired`；查询期间发现版本变化则重读或标记过期。执行变更仍重新核验，不把一个查询接口包装成强一致承诺。

启动时扫描已配置仓库中的未完成记录；涉及外部介质或远程未知结果的操作给出明确恢复入口，不后台盲目重做 push。操作历史显示结果与已产生效果，普通文本日志只用于诊断。

## 7. 代码职责拆分

按业务边界逐步拆分现有 `core/sync.rs`，不先建立大量空壳 trait：

| 模块                              | 负责内容                             |
| ------------------------------- | -------------------------------- |
| `core/protocol.rs`              | manifest、身份、摘要、快照、依赖验证；可纯函数测试    |
| `core/outbound.rs`              | 出站计划、对象基线、导出与发布恢复                |
| `core/replica.rs`               | 外网镜像导入、引用事务、开发仓库 fetch           |
| `core/review.rs`                | 回传接收、ReviewItem、patch 接收及应用、推送计划 |
| `core/branch.rs`                | 分支基准、rebase、worktree 及已有分支删除能力   |
| `core/operation.rs`             | 操作 ID、取消、结构化事件、恢复入口              |
| `core/repo.rs`                  | 仓库查询、角色识别、引用及对象信息                |
| `core/git.rs`、`core/storage.rs` | 保留现有执行器与存储原语，按需要小幅增强             |
| `commands.rs`                   | 参数转换、状态注入、后台执行、事件传递              |

模块可以在首次迁移对应业务时建立；暂时保留 `sync.rs` 作为旧 API 的适配入口。避免同时改变文件布局、协议和用户行为，便于回归定位。

## 8. 界面流程

界面以“快速完成同步”为目标，采用一个窗口、两个页签。内网提供“导出更新 / 导入回传”，外网提供“同步更新 / 回传提交”。精简交互见[界面规范](./ui-design.md)。早期独立 HTML 原型已经移除。

核心的阶段划分用于保证正确性和恢复，不要求用户逐步点击：

- 外网“同步更新”连续完成镜像导入和开发仓库获取引用，不改写本地工作分支。
- 内网“导入回传”连续完成接收、准备独立工作树和整理；正常完成后直接显示可推送分支。
- 导出自动选择包类型，正常路径不增加预览确认。全量选项按需展开。
- 推送保留一次提交确认。提交 OID、旧值及计划仍由核心固定，技术字段默认收起。
- 中断后显示已完成结果和“继续”动作；冲突、缺包、结果未知等只在发生时提示。
- 包身份、校验清单、命令日志和恢复细节按需查看，不常驻页面。

已处理的包不再成为新事项；组合动作中某一步失败，不抹去前面已经完成的效果。

## 9. 迁移计划

### 阶段 A：恢复边界与操作契约，不改包格式

- 首先修复共享状态恢复：导入前检查待恢复导出，恢复只更新归属字段，增加“回传中断 → 导入新包 → 恢复回传”的回归场景。
- 统一操作 ID、日志与取消，返回结构化错误。
- 状态读取错误明确展示；补齐开发仓库实际同步状态判断。
- 引入绑定 OID 的推送计划和远程结果核验。
- 保持现有命令适配，验证现有往返与界面回归。

验收：操作期间的后台查询不串日志；确认后分支被外部修改会阻止旧计划；停止批处理不会启动下一仓库。

### 阶段 B：回传接收与审查记录，不要求双端同时升级

- 为旧包计算本地接收键：规范化现有 manifest 与载荷摘要；无 manifest 的旧 bundle 单独标记为兼容来源并确认项目身份。
- 引入 inbox refs、接收标记、ReviewItem 和 patch 本地收件目录。
- 包文件不同路径重复导入返回原记录；已有分支不再被接收动作更新。
- 保存基准 OID、提交范围与 worktree 恢复信息。

验收：首次导入后 rebase，再导入同包仍返回原条目；多分支接收中断不会留下不可解释的半套引用。

### 阶段 C：协议与快照升级

- 两端提供 format 2 读写能力，在项目中显式切换发布格式。
- 新建项目生成 projectId；已有项目核对旧身份后由内网生成稳定 ID，首次 format 2 全量包携带迁移关联。
- 迁移前处理未完成发布、导入和 rebase；保存旧状态备份，不重置旧序号掩盖缺失记录。
- 新流从全量快照建立；旧包继续走兼容读取，但绑定 format 2 后禁止旧出站包修改新流游标。旧回传可进入兼容审查流程。
- 同一旧项目被各自独立迁移产生不同 UUID 时拒绝自动合并，要求选定权威内网源重新绑定。
- 旧版客户端无法读 format 2，因此升级前继续发旧格式；不能假设离线对端自动完成升级。

验收：新旧兼容边界明确，重建有独立流身份，同号异包拒绝，缺包可用全量恢复。

### 阶段 D：性能与维护性

- 启用 refs-only、基线对象保护及按需读取。
- 按业务拆分模块，清理不再使用的前端规则。
- 仅在测量证明确有必要时增加多项目并行。

不能把降级理解为直接读取新状态：旧应用只支持升级前备份对应的旧仓库副本。新协议产生数据后，优先前向恢复；回退需要保留新包与新开发提交，不能覆盖新状态文件后继续发旧流。

## 10. 验证与完成标准

保留现有 [端到端测试](../src-tauri/tests/e2e.rs)，尤其是完整往返、发布分支、引用变更、非法 manifest、导入失败重试、导出中断和 rebase journal 用例。新增验证围绕业务不变量，而不是函数调用次数。

| 验证场景                                | 预期                           |
| ----------------------------------- | ---------------------------- |
| 同一包从不同路径重复导入                        | 返回相同结果，无新审查分支，无重复 patch      |
| 同流同号、内容不同                           | 明确拒绝，不更新引用或游标                |
| 增量缺依赖、包号连续但对象缺失                     | 写引用前拒绝；可由新全量恢复               |
| 分支删除、force-push 回退、annotated tag 变化 | 快照精确对应，开发工作区不被修改             |
| 回传导出中断后尝试导入，再恢复回传                   | 导入先处理/阻塞于恢复记录；任何路径均不能倒退已接收游标 |
| 引用事务成功后 JSON 写失败                    | 重启从提交标记补齐状态，不重复导入            |
| 导出发布每一步中断、U 盘被移除                    | 原包原序号恢复，半成品不可导入              |
| 回传多分支接收时中断                          | inbox 引用成组提交，条目可重建           |
| patch 冲突后重启、重新选同包                   | 恢复原 am/worktree，不重复应用        |
| AI agent 或命令行在确认后提交                 | 推送计划过期；不能发送未确认新提交            |
| 远程在推送确认后变化                          | 非快进操作的明确 lease 拒绝覆盖变化        |
| push 已完成但客户端超时                      | 查询核实，无法判断时保留未知结果             |
| 取消批量同步                              | 已完成项保留，后续项不执行                |
| 状态 JSON 损坏                          | 展示恢复需求，不显示成新项目或零序号           |
| 重启或切换页面                             | 开发仓库是否需要 fetch 的判断保持准确       |
| 大小写冲突、路径别名、linked worktree          | 写入前发现能力/锁冲突，不自动迁移 ref 存储     |

测试分三层：协议纯函数与黄金数据、临时 Git 仓库集成测试及故障注入、少量界面契约测试。跨平台 CI 验证 Windows/macOS 的目录发布、文件锁、路径与取消行为；reftable 能力按实际 Git 版本检测。

实施完成的判断是：正常往返和每个关键中断点都有明确、可重试且不扩大副作用的结果；用户无需通过读日志猜测“到底同步到了哪一步”。
